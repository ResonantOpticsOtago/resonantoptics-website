# Maintaining the Resonant Optics website

This document is for whoever runs the machinery. Editors who only add news or
edit their profile should read [EDITING.md](EDITING.md) instead.

## 1. What this is

- A static website generated by [Hugo](https://gohugo.io) (extended edition)
  using the **Hugo Blox Builder "Research Group"** theme, Bootstrap flavour
  (`blox-bootstrap/v5`). The theme is installed as a *Hugo Module*, i.e. it is
  downloaded by Hugo at build time; nothing of the theme is copied into this
  repository. Versions are pinned in `go.mod`/`go.sum`.
- Source of truth: this GitHub repository, branch `main`.
- Live site: <https://resonantoptics.physics.otago.ac.nz>, served by the
  University of Otago physics web server. Publishing is **manual** (section 5).
- Preview site: Netlify builds the `draft` branch (section 6).

```
config/_default/   Hugo + theme configuration (hugo.yaml, params.yaml, menus.yaml, module.yaml)
content/_index.md  home page: a list of "blocks" (sections)
content/authors/   one folder per person: _index.md + avatar.jpg   <- people
content/post/      one folder per news item: index.md + images     <- news
content/publication/ one folder per paper, generated from BibTeX   <- publications
content/projects/  research project pages
content/people/, content/contact/   landing pages built from blocks
assets/media/      images referenced from the home page / blocks
scripts/           check_people.py (profile validation), publish.sh (publish)
.hugo-version      the Hugo version used everywhere (CI, Netlify, local)
netlify.toml       Netlify build settings (HUGO_VERSION must equal .hugo-version)
.github/workflows/ build.yml (build check), import-publications.yml (BibTeX import)
```

Abbreviations: CI = continuous integration (GitHub Actions); PR = pull
request; YAML = the `key: value` format used in every front matter block.

## 2. Pinned versions and how to upgrade them

| What | Where pinned | Current |
|---|---|---|
| Hugo (extended) | `.hugo-version`, `netlify.toml` (`HUGO_VERSION`) | 0.164.0 |
| Theme modules | `go.mod` / `go.sum` | blox-bootstrap/v5 @ 2024-10-12 commit (`v5.9.8-0.20241012174104-661cadc17327`) |
| `academic` (BibTeX converter) | `.github/workflows/import-publications.yml` | 0.11.2 |
| PyYAML (profile checker) | `.github/workflows/build.yml` | 6.0.2 |

**Upgrading Hugo.** Hugo makes breaking changes in minor releases. Before
changing the pin: read the release notes for every version in between
(<https://github.com/gohugoio/hugo/releases>), change `.hugo-version` *and*
`netlify.toml` on a branch, open a PR and let CI build it; look at the
"Hugo warnings" box in the job summary. Only merge if the build is clean.
CI fails if the two pins disagree.

**Theme.** The Bootstrap flavour of Hugo Blox is no longer developed
upstream (last release Feb 2024, last commit Oct 2024); the maintained line
is "HugoBlox Kit" (Tailwind). Expect the current theme to stop building on
some future Hugo release (it already triggers deprecation warnings:
`.Site.Data`, `.Site.AllPages`, `.Site.LanguageCode`). When that happens the
choices are: keep Hugo pinned at the last working version, or migrate to
HugoBlox Kit (a content migration, planned separately). To update the theme
within the Bootstrap line (if upstream ever tags another version):
`hugo mod get github.com/HugoBlox/hugo-blox-builder/modules/blox-bootstrap/v5@<version>`
then `hugo mod tidy`, build, review, PR.

**Never edit files that belong to the theme.** Customisations go into this
repository alongside the theme (`assets/scss/custom.scss`, `layouts/partials/...`
only if unavoidable, and if so document it here). An overridden theme file
silently stops receiving upstream fixes.

## 3. Branches and review

- `draft` — the working branch. Everyone in the GitHub organisation can
  commit directly (that is what the GitHub web editor does by default once
  `draft` is the default branch). Netlify shows it as a preview.
- `main` — what is published. Protected: changes arrive only by PR from
  `draft` (or a feature branch), and the "Build check" must pass.
- Anything experimental or large: a feature branch, PR into `draft`.

One-time setup on GitHub (repository → Settings):

1. Create the branch: `git switch main && git pull && git switch -c draft && git push -u origin draft`.
2. *General → Default branch* → `draft`. (New files added in the web editor and
   new PRs then target `draft` automatically.)
3. *Rules → Rulesets → New branch ruleset* for `main`: require a pull request
   before merging; require status check **build** (the job in
   `.github/workflows/build.yml`) to pass; block force pushes; block deletions.
   Rulesets on a public repository are free.
4. Optionally a ruleset for `draft` that only blocks force pushes and deletion.
5. *Collaborators and teams*: give the group **Write** access to the
   repository (needed to push to `draft`); keep **Admin** to one or two people.

Routine: editors commit to `draft` → look at the Netlify preview → a
maintainer opens a PR `draft` → `main`, waits for the green check, merges →
publishes (section 5).

## 4. The build check (CI)

`.github/workflows/build.yml` runs on every PR into `draft`/`main` and every
push to those branches. It

1. verifies `.hugo-version` and `netlify.toml` agree,
2. downloads exactly that Hugo release and verifies its SHA-256 checksum
   against Hugo's published checksums file,
3. runs `scripts/check_people.py` (errors fail the build),
4. builds the site; any Hugo *error* fails the job,
5. writes a de-duplicated list of Hugo *warnings* into the job summary
   (deprecation warnings are expected with this theme; anything else is
   usually a content mistake, e.g. an unknown `view:` name),
6. stores the built `public/` folder as a downloadable artifact for 14 days.

The workflow needs no secrets. It never deploys.

`.github/workflows/import-publications.yml` is the theme's stock BibTeX
importer: if a `publications.bib` file is committed to `draft` it converts new
entries into `content/publication/<key>/index.md` and opens a PR against
`draft`. It is the manual fallback until the Zotero job replaces it.

## 5. Publishing (manual)

Prerequisites on the machine that publishes: `git`, `rsync`, Hugo extended
**exactly** the version in `.hugo-version`, and a password-less SSH login to
the web server (key in `ssh-agent`). Copy `publish.conf.example` to
`publish.conf` and set `RSYNC_TARGET` (the file is git-ignored).

```
git switch main && git pull
scripts/publish.sh --dry-run    # builds, then lists what rsync would change
scripts/publish.sh              # builds and publishes
```

The script refuses to run unless you are on `main`, the working tree is
clean, and local `main` equals `origin/main`; so the server only ever
receives what GitHub has. `--force` skips those three checks (use it for
emergencies only). `DELETE_REMOTE="yes"` (default) removes files on the server
that are no longer part of the build; set it to `"no"` if the target folder
contains anything else. rsync compares file contents (`--checksum`) and
prints one line per changed file; a few dozen taxonomy/list pages (tag and
author pages) change on every build because Hugo orders pages with equal
dates non-deterministically. That is normal.

Alternative without a local Hugo: download the `public-run<id>` artifact of
the latest `main` build from the Actions tab, unzip, and `rsync` it yourself
with the same options as in the script.

Possible later automation (needs IT): a cron job on a university host that
downloads the latest `main` artifact or clones the repo and builds; or a
GitHub Actions job that rsyncs over SSH with a deploy key, if the web server
accepts inbound SSH from GitHub's runners.

## 6. Netlify preview

Netlify is used only as a preview; it never touches the university server.
Setup (once, on app.netlify.com): *Add new site → Import an existing project*
→ this GitHub repository. Build settings are read from `netlify.toml`
(Hugo version, build command, `public/` as publish directory). Under
*Site configuration → Build & deploy → Branches and deploy contexts* set the
**production branch to `draft`** and enable deploy previews for pull
requests. The site URL (something like `https://<name>.netlify.app`) is then
always the current state of `draft`. Give the URL to editors.

## 7. People profiles

One folder per person: `content/authors/<slug>/_index.md` plus
`avatar.jpg` (square). The folder name is the person's identifier and must
equal the first entry of `authors:` inside the file; posts refer to people by
this identifier, publications by the display name (`title:`). Group
membership is the `user_groups:` list; the groups shown and their order are
defined once in `content/people/index.md`. `scripts/check_people.py` enforces
these rules (run it locally with `python3 scripts/check_people.py`).

When somebody leaves: change `user_groups:` to `- Alumni` (and nothing else),
keep the folder; their publications and posts keep linking to the profile.

## 8. Publications

Generated with the [`academic`](https://github.com/GetRD/academic-file-converter)
converter from BibTeX: one folder per entry, named after the BibTeX key.
`academic import publications.bib content/publication/ --compact` creates
folders for new keys and leaves existing folders alone (no `--overwrite`), so
hand-made additions in a folder survive: a `featured.jpg` image, and
`featured` in the `publication_types:` list, which is what the home page's
"Featured Publications" block filters on. Changing BibTeX data of an existing
entry therefore requires either deleting the folder and re-importing, or
editing `index.md` by hand.

Planned: a scheduled GitHub Actions job exports the group's Zotero library
(group 6718035) via the Zotero API, runs the converter, and opens a PR
against `draft` when anything changed. See the project notes until it is in
place.

## 9. Access you need to take this over

- GitHub: **Owner** of the `ResonantOpticsOtago` organisation (at least Admin
  on the repository), so you can change rulesets and add people.
- The web server: an account that can `rsync` into the site's folder
  (ask physics IT; the path is in the current maintainer's `publish.conf`).
- Netlify: a team member on the Netlify site (or create a new one; nothing
  on Netlify is irreplaceable).
- Zotero: member of group 6718035 (once the Zotero job exists, also the API
  key stored as a repository secret `ZOTERO_API_KEY`, or none if the group
  library is public).
- Domain/DNS and the web server itself are run by the university; you never
  need to touch them.
